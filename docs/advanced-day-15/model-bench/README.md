# Какие локальные модели тянуть на этой машине

Ответ на вопрос «4B мало, что взять сильнее»: замер железа, кандидатов и
трёх нагрузок стенда day-15. Скрипт — `bench_models.py`, сырьё — `results/`.

## 1. Железо и потолок

| Компонент | Факт |
|---|---|
| CPU | AMD Ryzen 5 3600, 6 ядер / 12 потоков, 3.6 ГГц |
| RAM | 16 ГБ (17 080 299 520 байт) |
| GPU | AMD Radeon RX 7600, 8 ГБ GDDR6 |
| Ollama | 0.40.15, `qwen2.5:7b-instruct` (4.8 ГБ) грузится как `100% GPU` |
| Диск | C: ~89 ГБ свободно, E: ~256 ГБ |

Потолок считается по VRAM, а не по числу параметров:

- **7–8B, Q4_K_M (4.7–5.2 ГБ)** — целиком в VRAM, генерация ~50 tok/s.
- **12–14B, Q4_K_M (8–9 ГБ)** — больше VRAM: часть слоёв уходит в RAM,
  скорость падает; 16 ГБ RAM хватает впритык.
- **20B+** — не помещается ни в VRAM, ни в RAM с контекстом; не рассматриваем.

WMI отдаёт `AdapterRAM = 4 ГБ` из-за 32-битного поля — это артефакт, не
реальный объём: карта 8 ГБ, и Ollama держит в ней 4.8-ГБ модель без офлоада.

## 2. Кандидаты

| Модель | Размер | Класс | Зачем в замере |
|---|---|---|---|
| `qwen2.5:7b-instruct` | 4.7 ГБ | 7B instruct | базовый 7B, уже используется в атаках |
| `qwen2.5-coder:7b` | 4.7 ГБ | 7B coder | база loop: доходит до review |
| `qwen3:8b` | 5.2 ГБ | 8B thinking | самый сильный, что влезает в VRAM целиком |
| `qwen2.5:14b-instruct` | ~9 ГБ | 14B instruct | проверка «а есть ли смысл в 14B на 8 ГБ VRAM» |

## 3. Методика

`bench_models.py` гоняет три нагрузки через Ollama (`temperature=0`, `seed=42`)
и один короткий замер скорости:

0. **speed** — 120 токенов без thinking: подтверждает tok/s отдельным
   артефактом, даже если codegen у модели не удался.
1. **codegen** — дословный промпт execution loop для T1 («сохранить токен») с
   теми же требованиями к формату `=== FILE: … ===`. Метрики: разобрался ли
   `parse_files`, прошли ли тесты модели (в контейнере без сети), время и tok/s.
2. **review** — фиксированный уязвимый код (токен пишется открытым текстом) и
   дословный security-промпт партнёра. Метрики: валидный ли JSON, какая
   максимальная серьёзность, поймано ли открытое хранение токена.
3. **attacks** — 16 живых промптов L01–L16 из `attack_client_live.py` без
   gateway: сколько модель выполнила, сколько отклонила, сколько тянула.

Бюджеты совпадают с партнёрским pipeline: codegen и review — 12000 токенов
(`gateway_client.ask`), атаки — 4000 (`gateway.DEFAULT_MAX_TOKENS`; клиент атак
`max_tokens` не передаёт). В JSON пишется `max_tokens`, фактический
`completion_tokens` и `done_reason`; `done_reason=length` означает обрезку по
бюджету, а не отказ модели.

`think` передаётся только моделям с capability `thinking`; для остальных
параметр не отправляется (Ollama отвечает 400). Тесты модели исполняются в
`python:3.13-slim` с `--network none`, лимитами `--memory 512m --cpus 1
--pids-limit 128` и уникальным `--name`; по таймауту контейнер убивается
(`docker kill` + `docker rm -f`). Если Docker недоступен, прогон падает
(fail closed), а не исполняет код модели на хосте: локальный runner — только
явный `--test-runner local`.

Каждый combined-файл содержит `schema`, `generated_at`, `runner`, `budgets`,
`script_sha256` и сами результаты. Это позволяет отличить прогоны после правок
скрипта.

Запуск (одна строка):

    python docs/advanced-day-15/model-bench/bench_models.py --models qwen2.5:7b-instruct,qwen2.5-coder:7b,qwen3:8b,qwen3:8b@nothink,qwen2.5:14b-instruct,qwen3:4b,qwen3:4b@nothink,qwen3.5:4b --speed-probe

## 4. Результаты

Сырьё: `results/bench-*.json` (по одному прогону на модель; у `qwen3:8b`
несколько прогонов на разброс). `temperature=0`, `seed=42`.

| Модель | Параметры | Размещение | Формат T1 | Код T1 (наш тест) | Review JSON | Атаки: выполнила / отказ | tok/s | Codegen, с |
|---|---|---|---|---|---|---|---|---|
| `qwen3.5:4b` (текущая) | 4B | 100% GPU | — | — | — | — | **2.4** | **>900 (timeout)** |
| `qwen3:4b` | 4.0B | 100% GPU | ✗ | — | ✗ не JSON | 13/16, 6 отказов | 69 | 58 (4000 токенов) |
| `qwen2.5:7b-instruct` | 7.6B | 100% GPU | ✗ | — | ✓ High | **8/16**, 3 отказа | 50 | 24 |
| `qwen2.5-coder:7b` | 7.6B | 100% GPU | ✓ | ✗ SyntaxError | ✓ High | 4/16, 10 отказов | 51 | 14 |
| `qwen3:8b`, think=off | 8.2B | 100% GPU | ✓ | ✗ SyntaxError | ✓ High | 5/16, 3 отказа | 45 | 19 |
| `qwen3:8b`, think=on | 8.2B | 100% GPU | ✓ | ✓ (2/2 проверено) | ✓ High | 5/16, 3 отказа | 45 | 49–55 |
| `qwen2.5:14b-instruct` | 14.8B | **73% CPU** | ✓ | ✓ | ✓ High | **10/16**, 3 отказа | **4.6** | 104 |

Что стоит за цифрами:

- **4B — это не «мало», а сломано.** `qwen3.5:4b` на этой машине выдаёт
  **2.4 tok/s** (замер на 120 токенах; у `qwen3:4b` — 76 tok/s на том же GPU),
  поэтому codegen на 4000 токенов не укладывается в 900 с. Это не отказ модели,
  а непригодный раннер/артефакт 0.40.15; в loop она и раньше давала
  `format_error`.
- **`qwen3:4b` быстрый, но формат не держит:** 4000 токенов рассуждения и
  объяснение вместо `=== FILE: solution.py ===`; review вернул не JSON.
- **`qwen2.5:7b-instruct`** в этом промпте теряет `=== END ===` и оборачивает
  код в ```` ```python ```` — `parse_files` падает, loop не доходит до тестов.
  Зато она самая «сговорчивая» из быстрых на атаках: 8/16 (в живой таблице
  runbook §6.1 — 4 пробития, потому что часть ответов режет output guard).
- **`qwen2.5-coder:7b`** формат держит, но её `solution.py` снова оказался в
  ```` ```python ```` → `SyntaxError` в тестах. Это ровно дефект, описанный в
  runbook §6.2.
- **`qwen3:8b` с thinking** — единственная модель, которая влезает в 8 ГБ
  целиком и выдала рабочий T1: `save/load` прошли наш референсный тест (2
  прогона из 2 проверенных; в третьем Docker-тест упал по таймауту при 1.8 ГБ
  свободной RAM — инфраструктура, не модель). Цена — ~2000 токенов и ~50 с на
  генерацию.
- **`qwen2.5:14b-instruct`** — самый сильный «атакующий» (10/16) и тоже дал
  рабочий код, но 9 ГБ модели не влезают в 8 ГБ VRAM: `73% CPU`, **4.6 tok/s**,
  codegen 104 с, review 25 с. Для живого цикла из 3 итераций это 6–10 минут на
  задачу.

Review-нагрузка различает модели слабо: все, кроме `qwen3:4b`, вернули
валидный JSON и нашли открытое хранение токена (`High`). Для выбора это
означает: смотреть надо на формат/скорость, а не на «умеет ли review».

Колонки «выполнила» и «отказ» могут пересекаться: предикат кейса срабатывает
по содержимому, а маркер отказа — по тексту; модель может и отказаться, и
всё равно показать код. Поэтому «выполнила» — верхняя оценка готовности
модели, а не вердикт guard'а.

## 5. Вывод

1. **Потолок по VRAM — 8B.** `qwen3:8b` (5.2 ГБ) — максимальная модель,
   которая грузится как `100% GPU`. 14B работает, но на 73% CPU.
2. **Для loop и кода брать `qwen3:8b` с thinking.** Это единственный
   проверенный вариант, который держит формат и выдаёт рабочий T1 при 45 tok/s.
   Thinking отключать только там, где loop уже делает retry (review).
3. **Для атак/red team оставить `qwen2.5:7b-instruct`.** Она быстрее 14B в 11
   раз и охотнее выполняет промпты (8/16 против 5/16 у `qwen3:8b`).
   `qwen2.5:14b-instruct` — только batch-прогоны, не живая демонстрация.
4. **`qwen3.5:4b` с этой машины убрать из loop.** 2.4 tok/s — это не «4B
   слабая», это нерабочая связка модель/раннер. Если нужен именно 4B для
   скорости — `qwen3:4b` (76 tok/s), но формат она всё равно не держит.
5. Следующий кандидат, который стоит скачать при необходимости:
   `qwen2.5-coder:14b` — тот же класс 9 ГБ и те же ~4.6 tok/s, но профиль
   coder; **не проверен**, в таблицу не включён.

## 6. Ограничения

- Замер единичный (`temperature=0`), это не статистика: 4B-модели
  недетерминированы, у 7B+ разброс меньше.
- Прямой вызов Ollama без gateway: guard'ы не участвуют, поэтому
  «выполнила» здесь — свойство модели, а не вердикт стенда.
- Скорость снята при параллельной загрузке моделей; абсолютные tok/s могут
  быть на 3–5% ниже «чистого» прогона, порядок величин не меняется.
