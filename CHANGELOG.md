# Changelog

Хронология прохождения челленджа. Каждая запись — что сделано, какие выводы,
где посмотреть код.

Формат:
```
## День NN — <тема>
**Дата:** YYYY-MM-DD
**Задание:** <коротко что требовалось>
**Сделано:**
- ...
**Выводы:**
- ...
**Код:** challenge/days/day-NN-name/
```

---

## День 1 — Первый запрос к LLM через API
**Дата:** 2026-06-01
**Задание:** Минимальный код: отправить запрос в LLM, получить ответ, вывести.
**Сделано:**
- В архиве (`1-day/index.ts`): фрагмент TS-клиента в контексте Next.js-приложения.
- TS-порт (`challenge/days/day-01-first-request/`): автономный скрипт через
  `@challenge/core::LlmClient`.
**Выводы:**
- OpenAI-совместимый `/chat/completions` работает одинаково и для DeepSeek,
  и для OpenRouter — отличается только base_url и ключ.
- Минимальный запрос: `{model, messages}`.
**Код:** `challenge/days/day-01-first-request/index.ts`

## День 2 — Формат ответа
**Дата:** 2026-06-02
**Задание:** Один промпт с тремя уровнями контроля ответа.
**Сделано:**
- Без ограничений, JSON-формат, stop-sequence + `max_tokens=60`.
**Выводы:**
- Явное описание формата в промпте надёжнее, чем параметр `stop`.
- `max_tokens` пригодится для дня 8 (токены), но жесткий лимит обрезает ответ
  посередине мысли.
**Код:** `challenge/days/day-02-format/index.ts`

## День 3 — Способы рассуждения
**Дата:** 2026-06-05
**Задание:** Одну задачу решить 4 способами.
**Сделано:**
- Прямой ответ, "думай пошагово", мета-промпт, группа экспертов.
**Выводы:**
- "Пошагово" даёт самый структурированный и проверяемый ответ.
- Мета-промпт полезен, когда задача размытая — модель сама уточняет себя.
**Код:** `challenge/days/day-03-reasoning/index.ts`

## День 4 — Температура
**Дата:** 2026-06-07
**Задание:** Один промпт с `temperature = 0 / 0.7 / 1.2`.
**Сделано:**
- Три прогона, выводим рядом.
**Выводы:**
- 0 — для фактических ответов и кода.
- 0.7 — слоганы, краткие тексты, баланс.
- 1.2 — брейншторм, диверсификация идей; иногда рвёт логику.
**Код:** `challenge/days/day-04-temperature/index.ts`

## День 5 — Версии моделей
**Дата:** 2026-06-07
**Задание:** Сравнить слабую / среднюю / сильную модель.
**Сделано:**
- На OpenRouter: `gpt-4o-mini`, `gemini-2.0-flash`, `claude-3.5-sonnet`.
- Замеряем время и токены из `usage`.
**Выводы:**
- Слабые модели быстрее и дешевле, но путаются в многошаговых рассуждениях.
- На длинных промптах расход токенов растёт нелинейно — важно для дня 8.
**Код:** `challenge/days/day-05-models/index.ts`

## День 6 — Первый агент
**Дата:** 2026-06-09
**Задание:** Агент как отдельная сущность.
**Сделано:**
- `class Agent` с методом `say`, хранит system + history.
- REPL через `node:readline`: ввод пользователя -> LLM -> ответ.
**Выводы:**
- Логика запроса инкапсулирована в агенте, UI ничего не знает про HTTP.
- Этот агент — основа для всех последующих дней (контекст, токены, ветки).
**Код:** `challenge/days/day-06-agent/index.ts`

## День 7 — Сохранение контекста
**Дата:** 2026-06-10
**Задание:** История в JSON, восстановление при рестарте.
**Сделано:**
- `day-07-history.json` рядом с бинарником.
- `loadHistory` + `saveHistory` через `node:fs/promises` вокруг каждого хода.
**Выводы:**
- JSON хорош для демо; на проде нужен SQLite (см. день 9 — compression).
- Восстановление работает, только если системный промпт детерминирован.
**Код:** `challenge/days/day-07-persistence/index.ts`

## День 8 — Работа с токенами
**Дата:** 2026-06-11
**Задание:** Подсчёт токенов запроса / истории / ответа.
**Сделано:**
- Используем поле `usage` из ответа API.
- Копим `cum: Usage` по ходам.
**Выводы:**
- На длинной истории `prompt_tokens` растёт линейно — это главный аргумент
  за compression (день 9) и windowing (день 10).
- Без локального tokenization точный подсчёт невозможен — `usage` единственный
  честный источник.
**Код:** `challenge/days/day-08-tokens/index.ts`

## День 9 — Сжатие истории
**Дата:** 2026-06-11
**Задание:** Последние N как есть, остальное в summary.
**Сделано:**
- `summarize()` отдельным вызовом LLM.
- Пересоздаём summary каждые K сообщений, подставляем как `system`.
**Выводы:**
- Экономия на `prompt_tokens` видна сразу после первой компрессии.
- Качество ответа слегка падает, если summary слишком агрессивно сжало факты —
  отсюда мотивация для Sticky Facts (день 10).
**Код:** `challenge/days/day-09-compression/index.ts`

## День 10 — Стратегии контекста
**Дата:** 2026-06-14
**Задание:** Sliding Window / Sticky Facts / Branching + переключатель.
**Сделано:**
- Три класса, реализующих `ContextStrategy` из `@challenge/core`.
- Демо с одним и тем же сценарием (сбор ТЗ) на каждой стратегии.
- Branching: `checkpoint(label)` + `switchTo(id)`.
**Выводы:**
- Sliding — самый дешёвый, но теряет факты.
- Sticky Facts — лучший баланс, если правила извлечения фактов адекватные.
- Branching незаменим для "что если" сценариев и A/B тестинга промптов.
**Код:** `challenge/days/day-10-strategies/index.ts`
