## 0. Роль и цель

Ты — оркестратор (Tech Lead). Ведёшь задачу от инвентаризации данных до

## 1. Зафиксированные факты о данных (НЕ галлюцинировать, проверить на месте)

База: `challenge/.data/tg.sqlite` (вне git). Состояние на 2026-09-19:

- Чат: **«Факты в чате»**, `chat_key = '-1001736860345'`, `topic_id = 0`
  (не-forum, один поток). Это дискуссионный чат канала «Иди на факты глянь»
  (t.me/lookatfacts). Дотянут до **949 747 сообщений**, период
  **2021-12-28 → 2026-09-19**. Таблица: `tg_messages`, поля:
  `chat_id, topic_id, msg_id, from_id, from_name, text, date_iso,
  reactions_json ({emoticon:count}), reaction_total, fetched_at`;
  PK (chat_id, topic_id, msg_id). Доступ через `TgStore`
  (`challenge/src/core/tg/tgStore.ts`) — при необходимости расширяй его
  методами (конвенция core-reuse), сырой SQL в фиче-коде не размазывать.
- **`from_id` — стабильный ключ автора** (id Telegram-аккаунта),
  `from_name` — mutable display name (один человек = много имён; имя для
  показа = последнее по msg_id). Склейка авторов строго по `from_id`.
  Бывают `from_id IS NULL` (анонимные/сервисные) — их в профили не включать,
  но посчитать отдельно.
- `text` может быть пустым (media-only) — в LLM-анализ идут только `text <> ''`.
- Структуры реплик (reply_to) в схеме НЕТ — «кому отвечал» не восстанавливается,
  только временнáя близость. Это осознанное ограничение.
- В той же БД лежат ещё два чата (`-1001508192874` EVOLUTE, `-1001324711820`
  Антонов) — **не трогать**: профилировщик работает только с
  `-1001736860345`, фильтр по chat_key обязателен в каждом запросе.
- Рядом: `challenge/.data/rag.sqlite` (RAG-индекс) — к фиче отношения не имеет.

## 2. ЛЕНДМИН ПД (высший приоритет, без исключений)

В чате сообщения **сторонних частных лиц** (from_name/from_id — персональные
данные). Правила:

1. Профили, выдержки сообщений, статистика — **только локально**:
   `challenge/.data/` + авторизованные поверхности web (за auth-middleware,
   НЕ в PUBLIC_PATHS). Публичный `/demo`, `/style`, blog, TG-каналы —
   **запрещено** отдавать туда что-либо из профилей или сырых сообщений.
2. В UI профилей **не показывать `from_id`** (внутренний ключ ок в БД,
   наружу — только display name). Не показывать и не экспортировать
   списки «все авторы» за пределы авторизованной зоны.
3. Тон профилей — **описательный и нейтральный**: характеризуем манеру и
   роль в чате, не вешаем оценочных ярлыков и не диагностируем личность.
   Мат/цитаты в профиле — только как короткие иллюстрации манеры речи,
   не для смакования.
4. Удаление: владелец может удалить профиль (DELETE в UI/CLI) — данные
   сообщений при этом не трогаются.

## 4. Пайплайн (этапы джобы `tg-profile build`)

### 4.1 Инвентаризация (SQL, без LLM)
По `-1001736860345`: `GROUP BY from_id` → msg_count, text_count, first/last
date_iso, Σ reaction_total, доля пустых text. Отчёт: сколько авторов, топ-20
по объёму, распределение «1–5 сообщений» (молчунов не терять — им тоже нужен
короткий профиль). Этот отчёт показать владельцу ДО запуска LLM-фазы.

### 4.2 Признаки автора (SQL, per author)
- активность: msg_count, days_active (uniq date), медианный интервал,
  топ-часы суток, топ-дни недели;
- текст: медианная/макс длина, доля КАПС-сообщений (по эвристике), доля
  сообщений с эмодзи/ссылками/вопросами (оканчивается на «?»);
- реакции: Σ и max reaction_total, доля сообщений с реакциями;
- лексика: топ-15 значимых слов (стоп-слова ru+en отфильтровать — готовый
  список есть в `core/agents/telegramScan.ts` STOP_WORDS, переиспользовать).

### 4.3 Выдержки сообщений (SQL, per author, бюджет ~2500 символов на автора)
Стратифицированная выборка: топ-8 по reaction_total + 3 самых длинных +
12 равномерно-случайных по всей истории + первые 2 и последние 2. Каждая
выдержка: `[YYYY-MM-DD HH:MM] текст(≤280)`. Дедупликация.

### 4.4 LLM-профиль (per author, 1 вызов на «обычного», батчи на «тяжёлых»)
Вход: признаки 4.2 + выдержки 4.3. Выход — **строгий markdown**:
`portrait_short` (одна строка ≤120 знаков, для списка) и `profile_md`:
Кто в чате (роль/амплуа) · О чём и как пишет (темы, манера, лексика,
ритм — с мини-цитатами ≤100 знаков из выдержек) · Активность во времени ·
Знаковые моменты (2–4 факта из выдержек) · Чем известен в реакциях.

**Инварианты промпта:** факты ТОЛЬКО из выдержек; нет данных — так и писать
(«мало данных»), не сочинять; тон нейтрально-описательный; ответ только
markdown без преамбул. Промпт вынести в отдельный модуль-константу
(паттерн `web/lib/server/style-prompt.ts`), не строкой в логике.

### 4.5 Иерархический мерж для крупных авторов
Авторам с text_count > ~400: признаки+выдержки не влезают в один вызов —
делить историю на сегменты по времени (например по 2 года), профильить
каждый сегмент, затем **иерархический мерж** сегментных профилей в итоговый
(2 уровня максимум). ГОТЧА (проверено на стиле Антонова): локальная Ollama
с num_ctx 32768 **молча режет хвост** длинного промпта — не полагаться на
«и так влезет», бюджет символов на вход считать и ограничивать явно.

### 4.6 Режимы джобы
`tg-profile build [--limit N] [--only <id|name>] [--refresh]` — дефолт:
докупить профили только тем, у кого их нет или устарели (дельта по max msg_id
автора с момента последнего build — хранить в stats_json). Прогресс в stdout,
чекпоинт после каждого автора (крэш → продолжили с места). `tg-profile show
<name|id>` — печать профиля в терминал. Порядок обработки: сначала топ по
объёму (владелец раньше видит главное).

## 5. Веб-поверхность (вторая фаза, после CLI)

- Страница **`/tg/profiles`** (авторизованная, канон тул-страниц: SectionHead +
  Card + ui-kit, Manrope, без dev-жаргона, тексты ≤1 предложения):
  поиск по имени, список портретов (`portrait_short` + msg_count + период),
  клик → карточка профиля (`profile_md` отрендерить, from_id НЕ показывать).
- API: `GET /api/tg/profiles` (список/поиск) и `GET /api/tg/profiles/[id]`;
  `DELETE /api/tg/profiles/[id]` — удалить профиль (см. §2.4). Роуты НЕ
  добавлять в PUBLIC_PATHS. БД-доступ из web — через паттерн
  `lib/server/challenge.ts` (как весь web ходит в core).
- Тесты: unit на SQL-агрегаты признаков (фикстурная sqlite) + на модуль
  промпта (инварианты «нет фактов — нет утверждений»); e2e на страницу с
  моком API (паттерн `e2e/antonov.spec.ts`).

## 6. Бюджеты и отказоустойчивость

- Локальная Ollama: последовательно, 1 автор за раз; таймауты как в репо;
  флап Ollama → ретрай с бэкоффом ×2 (макс 3), потом пометить автора
  `profile_md = NULL` + причина в stats_json, идти дальше.
- Cloud-ключ тратить осознанно: по умолчанию профильить локально; cloud
  только флагом `--llm cloud`.
- Полный прогон ~15–25k авторов НЕ обязателен за один раз: джоба должна
  быть resumable и докатываемой; MVP-гейт качества — топ-100 авторов
  покрывают львиную долю трафика чата, их профилируем первыми.

## 7. Критерии приёмки

1. `tg-profile build --limit 100` доводит топ-100 до профилей без ручного
   вмешательства; повторный запуск — докупает только дельту.
2. Выборочная проверка 5 профилей владельцем: факты в профиле находятся в
   выдержках (нет галлюцинаций); «мало данных» у молчунов честное.
3. `/tg/profiles`: поиск находит по части имени; карточка рендерит профиль;
   гость на страницу и API получает 302/401; from_id нигде не показан.
4. `pnpm --filter challenge typecheck` и `pnpm --filter web typecheck` —
   чисто; vitest-тесты фичи зелёные; e2e-спека страницы зелёная.
5. В CHANGELOG.md запись фичи; ничего из профилей не утекло в публичные
   поверхности (проверить grep-ом по web: нет импортов профилей вне
   авторизованных роутов).

- Не переписывать TgStore под фичу деструктивно (только аддитивные методы).
