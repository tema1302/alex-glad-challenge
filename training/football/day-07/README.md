# Day 7 (футбольный трек) — свой датасет: NL → JSON матча (АПЛ/Челси)

Узкая повторяющаяся задача с проверяемым результатом: русскоязычная заметка
о футбольном матче → строгий JSON. Та же модель и рантайм, что в day-06
(Qwen2.5-0.5B-Instruct, CPU fp32) — сравнение честное, одна переменная.

## Задача и «верный ответ»

```json
{"home":"Челси","away":"Арсенал","home_score":2,"away_score":1,
 "scorers":[{"team":"Челси","player":"Мудрик","minute":34}, ...],
 "competition":"АПЛ","venue":"Стэмфорд Бридж"}
```

Верный ответ = точное совпадение всего JSON после каноникализации (сортировка
бомбардиров по минуте). Соглашения (в system prompt, см. `prompts.py`):
счёт всегда «дом:гости»; не назван стадион → домашний стадион принимающего;
«дома»/«на выезде» различаются; превью без счёта → null/null/[].

побед дома 106 / в гостях 108 / ничьих 90 (проверено до правок паттернов,
итоговые числа — в выводе скрипта).
Глазное ревью 30 случайных (`sample_review.py`, 2 итерации): найдены и
исправлены падежные ошибки («в матче Лиге чемпионов» → «Лиги чемпионов»),
склонение клубов («у «Арсенала»»), дубль клуба в голевой clauses,
«хет-трик» при 4 голах («покер»), превью без турнира (неверифицируемое поле).

## Обучение и сравнение (реальный прогон 2026-10-31, CPU)

Qwen2.5-0.5B-Instruct + LoRA r=16, system prompt `prompts.py`, 3 эпохи,
микро-батч 2 × grad-accum 4 (эффективный 8), lr 1e-4. Адаптер каждой эпохи
(`artifacts/adapter-epochN`). Стенка 7451.8 с (~2 ч 04 мин) — честная цена
CPU-тренировки на длинных JSON; инфраструктурный вывод: логиты fp32 на
длинных JSON — микро-батч ≤2 (иначе своп/segfault), чекпоинтинг на этой
машине деградировал до 2 потоков (не используем).

Кривая val loss: 0.0496 (эп.1) → 0.0401 (эп.2) → 0.0338 (эп.3) — расхождения
train/val нет, best = эпоха 3.

| Режим (один рантайм) | parse_ok | full_match | latency avg |
|---|---|---|---|
| tuned (адаптер вкл) | 30/30 | **11/30** | 18 839 ms |
| base-prompt (адаптер выкл, zero-shot) | 0/30 | 0/30 | 23 278 ms |

Итог против планок: none 0/30 → 11/30; prompt+few-shot (другой прогон)
4/30 → 11/30 (×2.75); base-prompt zero-shot в одном рантайме 0/30 → 11/30.
Per-field tuned: home 30/30, away 28/30, счёт 29/29, бомбардиры 19/30,
турнир 28/30, стадион 24/30. Регрессий tuned относительно base-prompt нет.

Разбор промахов (19 кейсов без full_match, по raw outputs):
1. **Много голов → потери/перестановки в scorers** (5+ голов: модель
   пропускает авторов или меняет атрибуцию клуба — eval-01, -02, -05);
   самое трудное поле (19/30).
2. **Каноникализация стадиона**: «на «Энфилде»» скопировано в том же
   падеже вместо канона «Энфилд» — частично дефект формулировки eval
   (несколько кейсов написаны с предложным падежом в кавычках).
3. **Редкие конвенции**: «уступил 0:1» с порядком дом:гости местами
   путается при гостевой победе.

Follow-up (если продолжим): больше примеров с 4+ голами и явной гостевой
победой; в eval писать стадионы только в канонической форме.

## Методология

- Одинаковые tokenizer/chat-template; temperature=0 (do_sample=False),
  seed=42; max_new_tokens=220.
- Метрики: parse_ok (JSON парсится), format_ok (ровно один JSON без прозы),
  full_match (все поля), per-field accuracy (home/away/scores/scorers/
  competition/venue), latency.
- base-prompt и tuned — одна загрузка модели, разница ровно адаптер
  (`disable_adapter()`); baseline из другого режима того же скрипта.

## Риски

- 318 примеров — нижняя граница; фокус на качестве разметки, не объёме.
- Имена игроков/клубов — разметочные метки парсера, не фактические составы.
